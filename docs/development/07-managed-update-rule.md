# Managed Update Rule

This chapter owns what a managed update may do to the live tree: how one exact official target is chosen and bound, which windows refuse conversation, how dirty local work is stashed rather than merged into history, what the authorized resolver may stage, and when a fresh rescue must precede destruction. It exists because a managed update rewrites the live tree in place under owner authority while other work may be running, so every step of it needs a stated custody rule.

- Keep the local work branch and the official update feed separate; the channel and branch topology live in ARCHITECTURE "8. Git Branching, CI, and Build" (`ouroboros/update_channels.py`).
- A preflight chooses one exact official target SHA. Apply binds to the disclosed base/target, closes new writers, drains direct turns, stops workers and tracked services, then re-plans before mutation; the update transaction is written before mutation, and writers reopen only after a verified abort/rollback or a healthy restart. Delayed evolution cleanup takes the same update lock and admission owner.
- Conversation admission is separate from repo-writing permission: the chat lanes refuse turns only during destructive windows (apply/replace/rollback prologue, materialization). While the ONE authorized assisted resolver holds the repository (`assisted_resolution` / `committing_assisted`), Main keeps answering, the registry guard still refuses repo tools to every other task, and steering reaches the resolver through the ordinary `steer_task` mailbox (`supervisor/worker_chat_lane.py::conversation_admitted_during_update`). The server's first-party packages are imported BEFORE conflict markers land in the live tree (`preload_owner_control_path`), because the packaged server runs embedded Python from the materialized repository.
- The assisted resolver imports a PINNED runtime, never the tree it is repairing. Before the merge is staged — while the checkout is still exactly `pre_update_sha` — that base's runtime code (`ouroboros/`, `supervisor/`, `prompts/`, `server.py`, `VERSION`) is published with verified content under `<DATA_DIR>/state/update_runtime/<sha>/` with a per-file manifest, and the transaction records the pin in its additive `runtime_pin` field (`supervisor/update_runtime.py`). Publication reads the git object database. A transaction that never recorded a pin may publish that exact base once, only when the snapshot directory is absent and the base contains the pinned-worker bootstrap. A recorded pin whose snapshot is missing or corrupt is a refusal: the on-disk tree is not deleted or replaced. Workers the assisted pool selects are plain custodied subprocesses whose first instruction is the SNAPSHOT's own `supervisor/update_runtime_boot.py` (`supervisor/update_runtime_worker.py`), because `multiprocessing`'s child entry rebuilds the parent's `__main__` from `server.py` and a conflicted `server.py` is a `SyntaxError` before the child runs a line. Initial start, replacement and boot recovery share that one factory. Both of the worker's `sys.path` insertions (the bootstrap, then `worker_main`) root in the snapshot; tool discovery and `__file__`-relative resources do too; `git_ops.REPO_DIR`, the agent's `repo_dir` and every tool access root stay the MUTABLE candidate, which is what the resolver edits and what its test gate runs. A missing, altered or unmanifested snapshot — and a base too old to contain the bootstrap — refuses to start a worker rather than fall back to the live tree: with resolution work already in the tree the transaction is re-phased `gate_blocked` so the partial merge survives for the owner, and without it the update rolls back. Ordinary multiprocessing workers outside an explicit selection are unchanged.
- Dirty local work never enters merge history: the apply stashes it and restores it as uncommitted content; a conflicting restore keeps the stash and discloses the recovery command. The reviewed assisted resolver runs only when Git reports a real conflict — filenames do not create a second update policy. Managed materialization and rollback run their internal `git reset --hard` without interactive confirmation; the explicit-confirmation rule applies to the owner-facing generic restore seam.
- The authorized resolver stages the complete merge including tracked binary files, and review receives their exact staged mode/blob/size plus the parent object ids; missing exact metadata blocks. This exception does not weaken the ordinary commit pipeline's binary policy.
- A managed merge commits only with proof that the full suite ran green on the exact candidate tree ("The commit gate mirrors the CI split" names the proof authority). Any non-commit terminal of the resolver rolls the live tree back and best-effort preserves the attempt on the deterministic failed-update branch; the fresh rescue snapshot, not that branch, is what rollback depends on.
- Take a fresh rescue before every destructive rollback and before boot-resume re-materialization — fail-open but disclosed durably at capture time, with its pointer in the update transaction (the choke point and why the pre-update snapshot is not enough: ARCHITECTURE "2. Startup / Onboarding Flow").
- Manual Restore reuses the same writer fence and pins the previous HEAD on a local recovery branch before reset. Promotion resolves the development SHA once and uses that exact SHA for both the local QA ref and any remote push.

Enforcement: `tests/test_update_merge_policy.py` (what the merge policy refuses), `tests/test_update_dirty_stash.py` (the dirty-tree path), `tests/test_update_hardening.py` and `tests/test_update_tx_corrupt_quarantine.py` (transaction integrity and quarantine), `tests/test_update_runtime_isolation.py` (the pinned resolver runtime, on real worker processes against a conflicted checkout).

External native hosts add no source updater: the source-selected launcher hook installs/verifies the artifact before a core generation, and managed post-boot readback precedes finalization. Failure uses existing rollback; worker self-restart keeps incomplete native adoption even when core SHA matches.
